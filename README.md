# chat-analyze

Юзербот Telegram (MTProto, обычный аккаунт) на Go. Ловит новые и отредактированные сообщения во всех
чатах аккаунта (личка, группы, супергруппы, форумы, каналы, комментарии), сохраняет их в PostgreSQL
(таблица `messages`, upsert) и помечает чат или тему прочитанным до этого сообщения.

Очередь заданий и сессия Telegram хранятся в PostgreSQL, внешних брокеров нет.

## Быстрый старт

Нужны Docker с compose и [just](https://github.com/casey/just).

```sh
cp .env.example .env     # заполните TG_API_ID, TG_API_HASH, TG_PHONE
just login               # один раз: вход в аккаунт (код и пароль 2FA вводятся интерактивно)
just up                  # postgres + миграции + сервис
```

`TG_API_ID` и `TG_API_HASH` выдаются на <https://my.telegram.org>. Сессия сохраняется в таблице `tg_session`.
Без сессии `run` сразу завершается с кодом 1 и ошибкой `telegram auth required` /
`telegram session not found, run "chat-analyze login"`, не подключаясь к Telegram.

Сервисы `migrate`, `app` и `login` используют один образ `chat-analyze:local`; `just up` собирает его
с версией и коммитом (`VERSION`, `COMMIT`), они видны в логе `service starting`.

Остановка: `just down`. Данные лежат в томе `pgdata`.

## Подкоманды

| Команда | Что делает |
|---|---|
| `chat-analyze run` | запуск сервиса (по умолчанию); без сессии завершается ошибкой, нужен `login` |
| `chat-analyze login` | интерактивный вход, сохраняет сессию в БД (сам применяет миграции) |
| `chat-analyze migrate up\|down\|status` | миграции схемы; нужен только `DATABASE_URL` |
| `chat-analyze healthcheck` | запрос к `/healthz` на `HTTP_ADDR`, код выхода 0/1 (для `HEALTHCHECK`) |
| `chat-analyze version` | версия и коммит |

Через just: `just login`, `just migrate status`, `just migrate down` и т. д.

## Конфигурация

Переменные окружения (шаблон в `.env.example`). Для compose дополнительно `POSTGRES_USER`,
`POSTGRES_PASSWORD`, `POSTGRES_DB`.

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DATABASE_URL` | — | обязательна, URL PostgreSQL |
| `TG_API_ID` | — | обязательна, > 0 |
| `TG_API_HASH` | — | обязательна, 32 hex-символа |
| `TG_SESSION_NAME` | `default` | имя сессии в `tg_session` |
| `TG_PHONE` | — | только для `login`, формат E.164 |
| `TG_RPS` | `10` | общий лимит запросов к Telegram API в секунду на аккаунт, > 0 и ≤ 100 |
| `WORKERS` | `1` | число воркеров, 1..64 (1 = строго последовательно) |
| `JOBS_MAX_ATTEMPTS` | `10` | число попыток задания до статуса dead |
| `JOBS_LEASE` | `2m` | срок аренды задания воркером, не меньше 1s |
| `JOBS_POLL_INTERVAL` | `1s` | интервал опроса очереди, не меньше 100ms |
| `JOBS_RETENTION` | `168h` | сколько хранить выполненные задания |
| `JOBS_DEAD_RETENTION` | `720h` | сколько хранить задания в статусе dead (их payload содержит текст сообщения), > 0 |
| `MARK_READ` | `true` | помечать сообщения прочитанными (не чаще раза в 3s на чат) |
| `SYNC_INTERVAL` | `15m` | период сверки диалогов с Telegram, не меньше 1m; `0` отключает |
| `HTTP_ADDR` | `:8080` | адрес HTTP-сервера (`/healthz`) |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |
| `LOG_FORMAT` | `json` | `json` или `text` |
| `TG_LOG_LEVEL` | `warn` | уровень внутренних логов gotd: `debug`, `info`, `warn`, `error` |
| `SHUTDOWN_TIMEOUT` | `30s` | время на корректную остановку, не меньше 1s |

`SHUTDOWN_TIMEOUT` должен быть меньше времени, которое оркестратор даёт на остановку до SIGKILL
(в `docker-compose.yml` у `app` стоит `stop_grace_period: 40s`; у `docker stop` по умолчанию 10s,
у Kubernetes `terminationGracePeriodSeconds` 30s). Если сервис не успевает остановиться за
`SHUTDOWN_TIMEOUT`, он завершается с кодом 1 (`shutdown timed out`).

## Нагрузка на Telegram API

Все запросы к API (воркеры, backfill, сверка диалогов, восстановление апдейтов) идут через общий лимитер: не больше
`TG_RPS` запросов в секунду (короткий всплеск до 3). Если любой запрос получил `FLOOD_WAIT_X`
(в логе `flood wait` с `method` и `wait_s`), все следующие запросы аккаунта ждут X+1s; ошибка
возвращается вызвавшему, повтора внутри лимитера нет. Задание, получившее `FLOOD_WAIT`, возвращается в
очередь через X+1s, не расходуя попытку (`JOBS_MAX_ATTEMPTS`). Если пауза не укладывается в срок
аренды задания, оно сразу возвращается в очередь.

Отметки о прочтении копятся в памяти: `save_message` только запоминает наибольший `message_id` по
чату (и теме форума), а отдельный цикл раз в 3s отправляет не больше одного `readHistory`
(`readDiscussion` для темы) на изменившийся чат. Отметка никогда не сдвигается назад (`tg_read_marks`).
При остановке несохранённые отметки отправляются после остановки воркеров, но не дольше половины
`SHUTDOWN_TIMEOUT`; не успевшие теряются (сообщения остаются непрочитанными до следующего сообщения в
чате). При старте и переподключении `getChannelDifference` выполняется не больше чем для 3 каналов
одновременно.

Размер пула соединений с БД: не меньше `WORKERS + 5` (каждый воркер держит соединение во время задания,
ещё одно постоянно занято под `LISTEN`). Явный `pool_max_conns` в `DATABASE_URL`
(например `...?sslmode=disable&pool_max_conns=20`) имеет приоритет.

## Пропуски в истории (backfill)

Задание `backfill_history` догружает историю любого чата (личка, группа, супергруппа, канал; `chat_id` —
marked id). Его ставят два источника: апдейт `channel too long` (Telegram не может отдать пропущенные
апдейты канала) и сверка диалогов (ниже). `min_id` = последний сохранённый `message_id` чата. Задания
`backfill_channel` из очереди прошлых версий миграция `00004` переводит в `backfill_history`. Отдельный воркер
догружает историю (`messages.getHistory`, до 1000 страниц по 100 с паузой 1s между страницами, то есть
до ~17 минут плюс задержка сети; аренда задания — 60 минут, с запасом на 30 минут `FLOOD_WAIT`) и ставит сообщения в очередь
`save_message` по возрастанию. Задание переживает ошибки, `FLOOD_WAIT` и перезапуск сервиса: короткий
`FLOOD_WAIT` пережидается внутри задания с повтором той же страницы (в сумме до 30 минут, в логе
`flood wait`), более долгий возвращает задание в очередь; и `FLOOD_WAIT`, и остановка сервиса возвращают
задание в очередь, не расходуя попытку (`JOBS_MAX_ATTEMPTS`). Повторный
`channel too long` до его выполнения не сдвигает `min_id` вперёд (`min_id=0` — «истории нет» — не затирает
известную границу). Если сообщений чата в БД ещё нет, берётся
только последняя страница (100 сообщений, в логе `backfill limited`, `reason=no_history`).

Сообщения из backfill проходят тот же разбор, что и живые апдейты: у них те же `topic_id` и
`thread_top_id`, а отметки о прочтении тем форума и веток ответов/комментариев (`readDiscussion`)
ставятся так же, после сохранения.

## Сверка диалогов (dialog sync)

Сервис сам приводит БД и состояние прочтения в соответствие с Telegram для всех диалогов (личка, боты,
«Избранное», группы, супергруппы, форумы, каналы, в том числе в архиве), что бы ни было пропущено: простой,
перезапуск, потерянные апдейты, первый запуск (менеджер апдейтов начинает с `getState` и не отдаёт
старое), `updates too long`.

Задание `sync_dialogs` ставится в очередь сразу после подключения и авторизации клиента (догрузка
после простоя начинается через секунды после старта), затем каждые `SYNC_INTERVAL`. В очереди не
бывает больше одного такого задания: пока проход ждёт или выполняется, новый не ставится. Задание
переживает перезапуск, `FLOOD_WAIT` возвращает его в очередь без расхода попытки, повторный проход
безопасен.

Проход листает `messages.getDialogs` по 100 диалогов (основной список, затем архив, `folder_id=1`) с паузой
1s между страницами, сохраняет пиров и их `access_hash` и для каждого диалога сравнивает `top_message` с
последним сохранённым `message_id`:

- история есть и `top_message` больше — `backfill_history` с `min_id` = последний сохранённый id;
  сообщения сохраняются через `save_message` и помечаются прочитанными как обычно;
- истории нет и `unread_count > 0` — догружаются **только непрочитанные** (`min_id` = `read_inbox_max_id`,
  не больше `unread_count` и не больше 1000 сообщений, самые новые) и помечаются прочитанными; старую
  историю таких чатов сервис не скачивает, при `unread_count = 0` такой чат не трогается;
- всё уже сохранено, но есть непрочитанные — отметка о прочтении до `top_message` через тот же
  накопитель отметок (раз в 3s);
- отметка «непрочитано» (`unread_mark`) снимается `messages.markDialogUnread`, непрочитанные упоминания и
  реакции — `messages.readMentions` / `messages.readReactions` (только когда догружать нечего);
- форум с непрочитанными: `messages.getForumTopics` (по 100 тем, с той же паузой); темы с непрочитанными,
  все сообщения которых уже сохранены, помечаются прочитанными (`readDiscussion` по id темы, тема General —
  вместе с чатом); темы с новыми сообщениями помечаются после их сохранения backfill-ом.

Пропускаются чаты, из которых аккаунт вышел или был удалён (`ChatForbidden`, `ChannelForbidden`, `left`,
`deactivated`), и пиры без полного `access_hash` (для min-пиров берётся сохранённый). При `MARK_READ=false`
сверка только догружает сообщения и ничего не помечает. Сохранение — upsert, поэтому сообщения, пришедшие
и через апдейты, и через сверку, не дублируются.

Нагрузка: проход, в котором догружать и помечать нечего, стоит только страниц `getDialogs` (~150 диалогов —
3 запроса: 2 страницы основного списка и 1 архива); запросы на отдельный диалог делаются только для
диалогов с непрочитанным. Отставшие чаты добавляют по заданию `backfill_history` (для небольшого пропуска —
2 запроса `getHistory`). Итог прохода в логе `dialog sync done` (INFO): `dialogs`, `skipped`,
`chats_behind`, `messages_behind` (оценка), `chats_marked_read`, `pages`, `duration_ms`.

Ограничения: непрочитанные ветки комментариев к постам каналов и ветки ответов в супергруппах, в которых
не появилось новых сообщений, не ищутся (у Telegram нет дешёвого списка непрочитанных веток, а запрос на
каждый пост слишком дорог) — они помечаются, когда в них приходит или догружается сообщение. Комментарии
к постам канала, если аккаунт не состоит в группе обсуждения, недоступны: этой группы нет в диалогах, и
сверка её не видит.

## Health

`GET /healthz`: `200 {"status":"ok"}`, если БД отвечает и Telegram-клиент подключён и авторизован;
иначе `503 {"status":"fail","db":"…","telegram":"…"}`.

## Логи

JSON в stdout (`LOG_FORMAT=text` для чтения глазами), ключи в snake_case: `time`, `level`, `msg`
(статическая строка), `component`, далее атрибуты. Уровни: `LOG_LEVEL` для кода сервиса и
`TG_LOG_LEVEL` для внутренних логов библиотеки gotd (по умолчанию `warn`). Сообщения об одном
сообщении Telegram связаны парой `chat_id` + `message_id`, об одном задании - `job_id` + `version`.

**Никогда не попадает в логи:**

- содержимое сообщений: `message`, `raw_text`, `entities`, подписи медиа, цитаты, названия тем;
- персональные данные: названия чатов, имена отправителей, `username`, телефоны, `sender_id`;
- секреты: `TG_API_HASH`, пароль из `DATABASE_URL`, телефон/код/пароль 2FA при `login`, байты сессии,
  `auth_key`, `access_hash`;
- сырые структуры: payload заданий, `tg.Message`/`tg.Updates` целиком, аргументы SQL-запросов,
  `Detail`/`Message`/`Where` ошибок PostgreSQL.

В логах только метаданные: идентификаторы (`chat_id`, `message_id`, `job_id`), типы, длины текста,
длительности, коды ошибок. Это обеспечено типами (`Secret`, `LogValuer`), единой точкой `internal/logx`,
линтерами и сквозным тестом с маркером в тексте.

## Разработка и тесты

Нужен Go 1.27.3 (`toolchain` в `go.mod` подтянется сам), `just`, Docker.

```sh
just lint               # golangci-lint (с тегом integration, как в CI)
just test               # unit-тесты (-race)
just test-integration   # интеграционные и сквозные тесты в docker compose
just vuln               # govulncheck
just ci                 # всё вместе
```

Базовые образы (golang, postgres) берутся из `mirror.gcr.io` (зеркало Docker Hub от Google), чтобы не упираться в лимиты Docker Hub на pull.

Интеграционные тесты (build tag `integration`) идут против настоящего PostgreSQL и запускаются в compose:
`just test-integration` поднимает временный postgres на tmpfs (`docker-compose.test.yml`) и прогоняет
`go test -tags=integration -race ./...`.

Их можно запустить и против локального PostgreSQL, указав `TEST_DATABASE_URL` (без неё тесты падают, а не
пропускаются; каждый тест создаёт собственную схему):

```sh
TEST_DATABASE_URL='postgres://postgres:test@localhost:5432/test?sslmode=disable' \
  go test -tags=integration -race -count=1 ./...
```

`just test-integration` использует отдельное имя проекта compose (`chat-analyze-test`) и не трогает
контейнеры, сеть и тома основного стека, поднятого через `just up`.

## CI

GitHub Actions (`.github/workflows/ci.yml`): lint (в том числе с тегом `integration`), unit с покрытием,
govulncheck, интеграционные тесты в compose и сборка Docker-образа. Образ публикуется в
`ghcr.io/a1ekseev/chat-analyze` только при push в `master` и тегов `v*`.

## Безопасность

Старые файл сессии и ключи `API_ID`/`API_HASH` (Python-версия) лежали в истории git. История переписана,
но это не отзывает уже скомпрометированные секреты. Обязательно:

1. завершите старый сеанс в Telegram (Настройки - Устройства - завершить сеанс);
2. перевыпустите `API_ID`/`API_HASH` на <https://my.telegram.org>.

Файл `.env` и `*.session` находятся в `.gitignore`, не коммитьте их.
